# 排错手册

> 本清单里的每一条都是**真实踩过的坑**，不是理论推演。按「症状 → 根因 → 修法」组织，遇到问题先查「快速定位表」。

## 判据先行：日志里的两种行

GitHub 会把 YAML `run:` 块的**每一行源码**着色回显到日志。于是一段带错误分支的脚本，日志里必然出现这样的**源码行**：

```
^[[36;1m  echo "::error::令牌已失效（HTTP 401）→ …"^[[0m
```

它看起来就像真报了错，但它只是脚本内容。

- **着色行 = 源码回显**（不可作为判据）
- **纯文本行 = 真实执行输出**（唯一判据）

同一段内容会成对出现两次，例如上面那行源码，与真实输出 `本次结果：今日已签到…` —— 恰好可以区分。

真正要看的是 `checkin-status HTTP=` 与 `daily-checkin HTTP=` 的**实际返回码**。

---

## 鉴权判定：只看真实 HTTP 码，绝不要 grep 响应体

**踩过的坑**：旧实现用 `grep -qi "401\|unauthorized"` 扫响应体来判断令牌是否过期。
但响应体里带**随机 UUID 的 requestId**，UUID 中恰好出现 `401` 就会**误判为令牌过期**
→ 脚本在调 `daily-checkin` **之前**就退出 → **当日积分没领到、连续签到中断**。

实测误判率约 **0.57%/次**；每天跑一次时，一年内约 **87%** 概率至少踩中一次。
这是典型的"看起来在增加鲁棒性，实际在制造故障"的写法。

**修法**：鉴权失败一律以 `curl -w '%{http_code}'` 拿到的**真实 HTTP 状态码**判定：

```bash
RESP="$(curl -s -m 15 -w '\n%{http_code}' -X POST "$API/..." -d '{}')"
HTTP_CODE="$(printf '%s' "$RESP" | tail -n 1)"   # 末行 = HTTP 码
BODY="$(printf '%s' "$RESP" | sed '$d')"          # 前面全部 = 响应体
case "$HTTP_CODE" in
  401|403) 令牌失效 ;;
  200)     ok ;;
esac
```

## 坑 1（最隐蔽）· YAML 块标量缩进 → 报「没有 workflow_dispatch 触发器」

**症状**：push 后 Actions 出现 `0s failure` 的运行；`gh workflow run` / dispatch API 报
`HTTP 422: Workflow does not have 'workflow_dispatch' trigger`，但打开文件明明写着 `workflow_dispatch`。

**根因**：`run: |` 是 YAML 块标量，标量内**所有行缩进必须 ≥ 该块首行缩进**。
若块内内联了多行解释器代码（如 `python3 -c "` 后续的 `import sys, json` 顶格），块标量被提前终止 → 整份 YAML 不合法 → GitHub 无法识别该工作流（连带看不到 dispatch 触发器）。

**修法**：块内所有行统一缩进；不要内联多行解释器代码，改用 runner 自带的 `jq`。
`scripts/push-cloud-files.sh` 与 `setup-cloud-repo.sh` 已内置推送前自检（顶格行会被拦截）。

> 判定技巧：**`0s failure` + 422 = 先怀疑 YAML 语法/缩进**，不要怀疑网络或权限。

## 坑 2 · contents API 更新已存在文件必须带 `sha`

同一路径第二次写入若不带 `sha`，contents API 返回 **409**。
脚本已自动先查 `--jq .sha`，有则走 update（附 `sha`），无则走 create。

## 坑 3 · Git Bash(MSYS) 会把 `/repos/...` 参数转成 Windows 路径

**症状**：`gh api` 报 `invalid API endpoint`，端点被写成 `C:/.../PortableGit/repos/...`。

**修法**：脚本已 `export MSYS_NO_PATHCONV=1` + `MSYS2_ARG_CONV_EXCL='*'`，且所有 API 端点**不写前导斜杠**，双保险。

## 坑 4 · 刚写入的 workflow 不能被立刻 dispatch

GitHub 需要几秒注册工作流。脚本已加「轮询 workflow id + 触发前 sleep」。手动重试也可。

## 坑 5 · 授权码页面的链接不要带 Markdown 加粗

`**https://github.com/login/device**` 复制时会带上 `**`，浏览器 404。给链接时不加粗。

## 坑 6（静默损坏，最危险）· `printf ... | retry ...` 会让重试写入空值

**症状**：脚本报告「✓ Secrets 已写入」，但云端运行报「缺少 Secrets」。

**根因**：管道只能被**第一次尝试**消费。若第 1 次 `gh secret set` 因网络抖动失败，
重试时子进程拿到的是**已耗尽的空 stdin**，而 `gh secret set` 对空输入会"成功地"写入空值并返回 0
→ Secret 被静默改坏，且脚本认为一切正常。

**修法**：新增 `retry_stdin`，把内容作为函数参数传入、**每次尝试现场重建管道**；
写入前还会打印令牌长度（`令牌长度 1319 字符`）作为非敏感的存在性佐证。

> 通用教训：**任何「管道喂 stdin + 重试」的组合都要检查管道是否可重放**；
> 或者改用 `--body "$value"`（argv 暴露风险）／`-f` 表单字段。

## 坑 7（与坑 6 同源）· 「在重试循环外只取一次」的值，取失败时重试会做**错事**

**症状**：`push_file` 对已存在的文件连续 5 次报 `"sha" wasn't supplied. (HTTP 422)`，
而前一次报的是 `TLS handshake timeout`。

**根因**：`sha="$(gh api ... --jq .sha || true)"` 在循环**外**只取一次。首轮网络抖动 → `sha` 为空
→ 被判定为「文件不存在」→ 走**新建**分支 → 对已存在文件必然报 422；此后每轮重试都用同一个空值，
**永远落在错误的分支上**。

**修法**：把「取 sha + 写文件」整体放进循环，每轮重新取 sha。

> **通用教训（同一个技能里踩了两次：坑 6 的管道、坑 7 的 sha）**：
> 凡是「取一次值 → 放进重试循环使用」或「管道喂 stdin → 重试」的写法，都要问一句
> 「这个值/这条管道在**第二次尝试**时还成立吗？」这类 bug 的可怕之处是**静默**：
> 要么写坏数据、要么 5 次重试全落在错分支而报一个与真因无关的错。

## 坑 8 · 块标量里写多行 shell 字符串，续行会掉缩进

**症状**：与坑 1 相同（`0s failure` + 422）。

**根因**：在 `run: |` 里写

```bash
MSG="${DETAIL}
时间：$(date)"
```

续行若与块起始缩进不一致（尤其**写成顶格**），块标量会被提前终止 → 整份 YAML 失效。

**修法**：**禁止在块标量里出现多行 shell 字符串**，一律用单行 `printf` 拼装换行：

```bash
MSG="$(printf '%s\n时间：%s\n详情：%s' "$DETAIL" "$NOW" "$LINK")"
```

并加**双保险**：① awk 顶格行自检；② 用 pyyaml 做**真解析**（还断言 `workflow_dispatch` 存在、
每个 `run` 块以换行正常结尾），推送前拦截。

> 「知道规则」不等于「写的时候不出错」——这个坑在本技能的开发过程中又踩了一次，所以才把自检做成两道。

## 坑 9（静默失效）· 用「剔除 ESC 字节」过滤日志，在 Windows 上等于没过滤

**背景**：见上面「判据先行」。读日志时极易把源码行误判为错误。

**踩的坑**：第一版按「剔除含 ESC（`\x1b`）的行」实现 —— 结果**一行都没剔掉**。实测发现：

| 判据 | 实测行数（同一份 162 行日志） |
|---|---|
| 含真实 ESC 字节（`0x1b`） | **0 行** |
| 含**字面串** `^[[` | **90 行** |

⇒ **Windows 下 `gh.exe` 不输出真实 ESC 字节，而是把 ANSI 序列输出成可打印字符** `^[[36;1m`。
所以 `grep -v $'\033'`、`sed 's/\x1b\[[0-9;]*m//g'` 这类写法在 Windows 上**静默失效**（不报错、也不生效）。

**修法**：**同时剔除两种形态**，跨平台通用：

```bash
| grep -vF -e '^[[' -e $'\033'      # 字面 ^[[（Windows gh）+ 真实 ESC（Linux/macOS gh）
| awk -F'\t' '{print $NF}'          # 去掉 "job<TAB>step<TAB>时间戳 " 前缀
```

⚠️ `grep` 必须用 `-F`（固定字符串），否则正则里 `^[` 会被当成字符类锚点。

> **教训**：这类「过滤条件写错但脚本照常退出 0」的问题**不会报错**，只会让噪声留在输出里 ——
> 必须**看一眼真实输出**才能发现（`grep -c` 数一下命中行数就能立刻暴露）。

## 网络现实（国内直连，落地前必读）

本机到 GitHub 的连通性是**抖动可用**，不是稳定可用：

| 目标 | 实测 |
|---|---|
| `github.com` | 5 次请求 2 通 3 超时（成功时耗时 3~8s） |
| `login/oauth/access_token` | 曾出现 `unexpected EOF` → 设备码授权中途失败 |
| `api.github.com` | 同样时通时断（通了正常，断了 `000`） |

由此产生的设计取舍：

1. **写文件走 GitHub API，不走 `git push`** —— 避开 github.com 的 git/ssh 通道，只依赖 api.github.com。
2. **所有 gh 调用带重试**（内置 5 次指数退避），用"多试几次撞上通的那几秒"换成功率。
3. **首次授权与网页登录建议开代理**：设备码流程要访问 `github.com/login/device`，是抖动最明显的路径。
4. **令牌镜像同样只依赖 api.github.com**：不开代理时只是"这次推不上去"，**不会写坏云端**（脚本会中止并保持原值）。

> **日常定时签到跑在 GitHub 云端，不需要本机任何网络访问。** 以上问题只影响"本机配置阶段"和"手动补签"。

## 无代理时的备选运行环境

| 方案 | 优点 | 代价 |
|---|---|---|
| 腾讯云函数 SCF / 阿里云 FC 定时触发器 | 国内直连稳定、无需代理 | 控制台手动建函数 + 定时触发器，令牌填环境变量 |
| 腾讯云轻量服务器 cron | 完全自主 | 需购机（约 ¥24+/月起），为每天 100 积分不划算 |
| 本机睡眠唤醒 | 零凭据变动、零外部依赖 | 电脑需插电睡眠；彻底关机/断电时失效 |

> 本方案的工作流与 `notify.sh` 逻辑（取令牌 → 调接口 → 通知）可直接移植到上述任一环境。

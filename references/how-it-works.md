# 它是怎么工作的

理解这四件事，你就能自己判断"某天没签到"到底是哪一环出了问题。

## 一、整体链路

```
你的电脑（只做两件事：配置时推一次令牌；之后每周镜像一次新令牌）
   │
   │  gh secret set WB_CHECKIN_TOKEN   ← 令牌只经管道，不显示、不落盘
   ▼
你的私有 GitHub 仓库
   │
   ├─ .github/workflows/checkin.yml   定时器（北京 08:30 主干 / 20:30 兜底）
   ├─ notify.sh                        通知逻辑
   └─ diag-token.sh                    令牌体检逻辑
   │
   ▼
GitHub Actions runner（ubuntu-latest，在 GitHub 机房）
   │  curl POST copilot.tencent.com/v2/billing/meter/daily-checkin
   │  Header: Authorization: Bearer <Secret 里的令牌>
   │
   ├─ code=0      → 签到成功 → 推送通知（若兜底那次才签上，标题标注"兜底补签成功"）
   ├─ code=10001  → 今日已签到（幂等）→ 静默，不推送
   └─ HTTP 401    → 令牌过期 → 推送「签到异常」
```

**关键点：日常签到全程不经过你的电脑。**

## 二、令牌寿命与"无感续期"

| 观测项 | 实测值 |
|---|---|
| accessToken 有效期 | **恰好 55.00 天**（`exp - iat`） |
| `auth.expiresIn` / `refreshExpiresIn` | 4752000 秒（55 天）/ 5184000 秒（60 天），**每次刷新都重新计算** |
| 令牌类型 | Keycloak JWT（`iss=https://www.codebuddy.cn/auth/realms/copilot`），scope `openid profile offline_access` |

**桌面端每次运行都会用 refreshToken 换发一把全新的 accessToken，并把寿命重置为 55 天。**

所以"无感续期"不需要碰 refreshToken、不需要动协议 —— 只要把本机这把新令牌**自动镜像**到云端 Secrets 即可。

```
令牌寿命 55 天  ÷  镜像周期 7 天  =  约 8 倍余量
```

某周没开机漏一次，下周补上也不会过期；指纹未变时脚本零网络请求、1 秒内退出。
只有**连续 55 天完全不开机**令牌才会真过期 —— 打开桌面端会自动换发，再跑一次镜像脚本即恢复。

> ⚠️ **关键机制（极易搞错）**：令牌刷新由**桌面端运行/交互**触发，**与自动化任务无关**。
> 实测佐证：某天签到自动化 09:03 就跑完了，而登录态里的刷新时间是当天下午 13:36 与 15:52（都是人在用桌面端时）。
> ⇒ **停用任何自动化都不影响令牌新鲜度**：只要日常在用桌面端，登录态里就一直是"刚签发、够用 55 天"的令牌。

### 常见疑问：本机换发新令牌后，云端手里的旧令牌会失效吗？

**不会。** accessToken 是**无状态 JWT**，服务端只按它自身的 `exp` 校验，**不存在"单会话互踢"**。

实测（两次独立运行，时序无歧义 —— 这是关键，否则结论站不住）：

| 时刻 | 事件 |
|---|---|
| T+0 | 本机换发令牌 A |
| T+6min | 令牌 A 镜像到云端 |
| **T+51min** | **重启桌面端 → 本机换发令牌 B** |
| **T+72min** | 云端用**旧令牌 A** 探针 → **HTTP 200** |
| T+74min | 同场体检：新令牌 B → 200、旧令牌 A → 200、**人为损坏令牌 → 401** |

⇒ 云端调用发生在**本机已持有更新令牌之后 21 分钟**，两把相隔 51 分钟签发的令牌**同时**被接受。
**结论：每周镜像时序安全 —— 周二~周日云端不会因桌面端刷新而 401。**

**必须避开的两个陷阱（早期结论出错的根源）**：

1. `daily-checkin` 返回 **`code=10001`（今日已签到）不能**用来证明令牌有效 ——
   它只说明"调用之前已经有人签过"，而那个人可能是本机脚本，也可能是**桌面端自身在检测到使用后自动签到**。
   只有 **`code=0`** 的那次调用才是"第一名"。
2. **结论必须卡住时间先后**。曾经据"云端某次跑出 200"断言此事，复查发现本机换发新令牌比那次调用**晚约 5 秒** ——
   当时本机还是同一把令牌，**根本没构成对照**。

**复验方法**：

```bash
bash scripts/token-fingerprint.sh     # 本机这把：指纹/签发时间/剩余（不打印令牌）
bash scripts/cloud-diag.sh            # 云端那把：同款 + 真实 HTTP 码 + 坏令牌对照
```

判读：对照令牌（签发更早）仍 `200` ⇒ 换发**不会**吊销旧令牌；
`401/403` ⇒ 会被吊销，需把镜像频率从每周加密到每天（成本仍近零）。

> ⚠️ 体检结论里**必须**有"人为损坏的令牌 → 401"这一行，否则那些 200 不可信（无法排除接口放行）。
> 唯一能推翻此结论的情况：服务端将来上线"新登录踢掉旧会话"类策略 —— 届时体检会立刻检出。

## 三、幂等：为什么"补签"是零风险的

签到接口**幂等**：

| 返回 | 含义 |
|---|---|
| `code=0` | 本次是当天第一签，成功领取 |
| `code=10001` | 当天已签过 → 不重复领取、**也不算失败** |

因此：

- **定时任务配两条 cron 零风险**：兜底那条只会在"主干真的漏了"时才签到成功，其余情况静默跳过。
- **拿不准签没签时，直接补跑即可**。
- ⚠️ 注意：`checkin-status` 的 `today_checked_in` 字段**不可靠**（签到成功后仍可能为 `false`），
  所以幂等性主要靠 `daily-checkin` 的 `code=10001` 兜底。

## 四、为什么需要两条 cron（GitHub 定时任务语义）

| 事实 | 后果 |
|---|---|
| GitHub 定时任务有 **5~30 分钟延迟**属正常 | 不要指望精确到分钟；按"当天完成"计即可 |
| 官方文档写明：高负载时定时事件会**延迟**，排队中的 job **甚至可能被直接丢弃** | 单条 cron 不保证必达 |
| 建议避开整点 | 故取 08:30 / 20:30 |

⇒ 只有一条 cron 时，若那次运行整体没发生，**当天就没有第二次机会**；
又因为"今日已签到"被静默，用户连"今天没签上"都不会被通知到。
**这就是兜底 cron 的必要性来源。**

兜底那次才签上是有意义的信息：说明主干当天没成功。
`Notify` 步骤透传 `github.event.schedule` 判定触发来源（定时事件下，它的值就是命中的那条 cron 表达式，
这是官方支持的用法），此时标题改为「WorkBuddy 兜底补签成功」。

> 残余盲点（cron 解决不了）：**两条都没跑**（工作流被停用、GitHub 大范围故障）时不会产生任何通知，
> 需靠 `cloud-run-checkin.sh --status` 或定期巡检发现。

## 五、为什么没做"云端自续期"（值得知道的技术判断）

`grant_types_supported` 里确实有 `refresh_token`，token 端点也存在：

```
https://www.codebuddy.cn/auth/realms/copilot/protocol/openid-connect/token
```

技术上可让云端自己换令牌，但有两个硬问题：

1. **轮换风险**：若服务端启用刷新令牌轮换，云端一刷新就会把桌面端登录态顶下线（需重新登录）。
   而桌面端天天在跑、会不断刷新 —— 云端存的那把 refreshToken 几乎立刻过期，
   **这条路在"桌面端在用"的前提下本身就不可靠**。
2. **回写难题**：Actions 运行器无法直接改仓库 Secret，要回写新 refreshToken 得再存一个 PAT，凭据链变长。

另外本地登录态里的 `auth.refreshToken` 是**加密对象**，提取需要走 WorkBuddy.exe 解密链路。

**结论：本地镜像已足够，且零风险；云端自续期不值得做。**

| 项 | 数值 |
|---|---|
| 单次运行耗时 | 约 15~20 秒 |
| 每日运行 | 2 次（主干 + 兜底） |
| 每月用量 | 约 **18 分钟** |

余量充足（约 1%）。
